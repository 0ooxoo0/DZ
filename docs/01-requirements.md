# Требования

## 1. Формализация исходного задания

Исходное ТЗ написано в свободной форме. Ниже оно приведено к проверяемому виду: каждый пункт
имеет идентификатор, источник и критерий приёмки.

## 2. User stories

| ID | User story | Приоритет |
|---|---|---|
| US-01 | Как сотрудник банка, я хочу получать список банковских продуктов, рекомендованных конкретному клиенту, чтобы предлагать клиенту только релевантные услуги | Must |
| US-02 | Как сотрудник банка, я хочу, чтобы рекомендации рассчитывались по правилам банка, а не выбирались вручную, чтобы предложение было одинаковым для всех сотрудников | Must |
| US-03 | Как сотрудник банка, я хочу получать пустой список вместо ошибки, если клиенту нечего предложить, чтобы отличать «нет предложений» от сбоя сервиса | Must |
| US-04 | Как маркетолог банка, я хочу добавлять новый продукт с набором правил без переписывания существующего кода, чтобы развивать систему итерациями | Should |
| US-05 | Как сотрудник банка, я хочу, чтобы сервис не изменял данные клиентов, чтобы исключить риск порчи выданной базы | Must |
| US-06 | Как сотрудник банка, я хочу получать понятную ошибку при некорректном идентификаторе клиента, чтобы отличать ошибку в запросе от ошибки сервиса | Should |

## 3. Functional Requirements

| ID | Требование | Критерий приёмки |
|---|---|---|
| FR-01 | Сервис предоставляет метод `GET /recommendation/{user_id}` | Запрос возвращает `200 OK` |
| FR-02 | Формат ответа соответствует ТЗ: `{"user_id": <uuid>, "recommendations": [{"name", "id", "text"}]}` | `Content-Type: application/json`, поля и их имена совпадают с ТЗ |
| FR-03 | Поле `user_id` в ответе — строка UUID, совпадающая с переданной | Для `cd515076-…-8d4fcb79f42d` ответ содержит то же значение |
| FR-04 | Если ни одно правило не выполнено, возвращается `200 OK` и пустой массив `recommendations` | Для клиента без операций `recommendations` = `[]` |
| FR-05 | Рекомендация «Invest 500» (`147f6a0f-3b91-413b-ab99-87f081d60d5a`) выдаётся при выполнении всех правил: есть продукт типа `DEBIT`; нет продуктов типа `INVEST`; сумма пополнений по `SAVING` строго больше 1000 ₽ | Тесты `Invest500RuleSet`, сквозной тест на `cd515076-5d8a-44be-930e-8d4fcb79f42d` |
| FR-06 | Рекомендация «Top Saving» (`59efc529-2fff-41af-baff-90ccd7402925`) выдаётся при: есть продукт типа `DEBIT`; сумма пополнений по `DEBIT` ≥ 50 000 ₽ **или** сумма пополнений по `SAVING` ≥ 50 000 ₽; сумма пополнений по `DEBIT` строго больше суммы трат по `DEBIT` | Тесты `TopSavingRuleSet`, сквозной тест на `d4a4d619-9a0c-4fc5-b0cb-76c49409546b` |
| FR-07 | Рекомендация «Простой кредит» (`ab138afb-f3ba-4a93-b74f-0fcee86d447f`) выдаётся при: нет продуктов типа `CREDIT`; сумма пополнений по `DEBIT` строго больше суммы трат по `DEBIT`; сумма трат по `DEBIT` строго больше 100 000 ₽ | Тесты `SimpleCreditRuleSet`, сквозной тест на `1f9b149c-6577-448a-bc94-16bea229b71a` |
| FR-08 | Клиент считается пользующимся продуктом, если по продукту есть хотя бы одна операция | `RecommendationRepository.hasProductOfType` — `COUNT(*) > 0` |
| FR-09 | Все правила одной рекомендации объединяются логическим «И», правила с «ИЛИ» — логическим «ИЛИ» | Тесты граничных значений в `RecommendationRuleSetTest` |
| FR-10 | Сервис поддерживает несколько наборов правил и опрашивает все, возвращая все совпадения | `RecommendationService` инжектирует `List<RecommendationRuleSet>` |
| FR-11 | Некорректный `user_id` отклоняется с `400 Bad Request` | Сквозной тест `rejectsMalformedUserId` |

## 4. Non-Functional Requirements

| ID | Требование | Как обеспечено |
|---|---|---|
| NFR-01 | Приложение — Spring Boot | `spring-boot-starter-parent` 3.2.3, `@SpringBootApplication` |
| NFR-02 | Источник данных — выданная БД `transaction.mv.db`, URL `jdbc:h2:file:./transaction`, драйвер `org.h2.Driver`, режим `READ_ONLY` | `application.properties`, `spring.datasource.hikari.read-only=true` |
| NFR-03 | Для запросов используется только `JdbcTemplate`; JPA/Entity не применяются | В коде отсутствуют `@Entity`, `JpaRepository`, `spring-boot-starter-data-jpa` |
| NFR-04 | Производительность SQL: общие правила выделены в параметризованные запросы вместо отдельного SQL на правило | Два запроса в `RecommendationRepository`, параметры — тип продукта и тип операции |
| NFR-05 | Агрегация выполняется на стороне БД | `SUM(amount)` и `COUNT(*)` в SQL |
| NFR-06 | Компоненты пригодны для модульного тестирования с Mockito и JUnit | Зависимости через конструктор, `RecommendationRuleSet` — интерфейс |
| NFR-07 | База данных не изменяется приложением | Нет операций `INSERT/UPDATE/DELETE`, `spring.sql.init.mode=never` в `main` |
| NFR-08 | Архитектура допускает развитие: новый продукт — новый класс, без правки существующих | `RecommendationRuleSet` + `@Component`, подхват через `List<RecommendationRuleSet>` |
| NFR-09 | Логирование и обработка ошибок не раскрывают внутренние детали клиенту | Маппинг ошибок через `ResponseStatusException` |
| NFR-10 | Сборка и тесты воспроизводимы одной командой | `mvn clean verify` |

## 5. Ограничения

- Язык и платформа: Java 17, Spring Boot 3.x, Maven.
- База данных — только чтение; вторая БД не создаётся.
- Аутентификация и авторизация в объём первой итерации не входят.
- Изменение текстов и правил продуктов требует пересборки приложения (значения заданы в коде).
