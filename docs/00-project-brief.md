# Краткое содержание проекта

## Заказчик и цель

Банк «Стар» внедряет рекомендательную систему для маркетинга: сотрудник банка должен видеть,
какие продукты предложить конкретному клиенту. Цель первой итерации — MVP-сервис, который по
идентификатору клиента возвращает перечень банковских продуктов, подходящих этому клиенту по
заданным бизнес-правилам.

## Объём первой итерации

Входит:

- один метод REST API `GET /recommendation/{user_id}`;
- три набора правил (Invest 500, Top Saving, Простой кредит) из таблицы ТЗ;
- чтение выданной банком БД `transaction.mv.db` через `JdbcTemplate`;
- модульные и сквозные тесты.

Не входит:

- управление сущностями БД (пользователи, продукты, операции) — база только для чтения;
- авторизация и аутентификация вызовов;
- кэширование и внешние очереди;
- административный интерфейс редактирования правил.

## Исходные данные

Файловая база H2 `transaction.mv.db`, три таблицы: `users`, `products`, `transactions`.
База наполнена данными, приложение в неё не пишет. Подключение:
`jdbc:h2:file:./transaction`, драйвер `org.h2.Driver`, режим `READ_ONLY`.

## Ключевые решения

| Решение | Обоснование |
|---|---|
| `JdbcTemplate` вместо JPA | Сущности не принадлежат приложению, схема выдана банком; ТЗ прямо запрещает Entity/JPA |
| Два параметризованных SQL-запроса на все правила | Правила сводятся к «есть продукт типа X» и «сумма операций вида Y по продуктам типа X»; один запрос на правило означал бы дублирование SQL |
| Агрегация в SQL, сравнение в Java | Суммы считает БД (меньше данных в приложении), пороги и логика «И/ИЛИ» — в Java (проще тестировать) |
| Правило = отдельный `@Component` | Новый продукт добавляется новым классом без правки сервиса и контроллера |
| `record` для DTO | Неизменяемые объекты без геттеров и сеттеров, меньше кода |
| Строгий разбор `user_id` | Некорректный идентификатор — `400 Bad Request`, а не `500` |

## Ограничения и допущения

- Значения типов продуктов (`DEBIT`, `CREDIT`, `INVEST`, `SAVING`) и операций (`DEPOSIT`, `WITHDRAW`)
  взяты из выданной БД; при их изменении правится перечисление в коде.
- Пороги правил (1000 ₽, 50 000 ₽, 100 000 ₽) заданы в классах правил; вынос в конфигурацию —
  задача следующей итерации.
- Пустой ответ не кэшируется, внешних зависимостей у сервиса нет.
